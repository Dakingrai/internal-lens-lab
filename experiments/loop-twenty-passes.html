Experiment title

Planned

In short

The sentence this experiment should let us say: when Inkling 2 Mini's loop runs past the 3 passes it was trained with, the logit lens finds the intermediate at [more / the same / fewer] questions than after pass 3, and the model [keeps / changes / loses] the answer it gives at 3 passes.

Two things make the question worth asking. Lee et al. found the logit lens reads well at the end of each pass of the loop, and that one coordinate of the state turns from a large positive value after passes 1 and 2 to a large negative one after pass 3, which they read as the model not expecting another pass. And the model's code accepts any number of passes, though the model card and the nnsight post both say Inkling 2 Mini was trained with exactly 3.

We run the model once per question with the loop set to 20 passes, read the logit lens after every pass, and record what the model would answer if it stopped after that pass. The 10 practice questions and WorkspaceBench's 238 single-token questions are run and shown apart. The result is meant to be read by eye, in a readout grid that steps through the passes; two counts per pass say where to look.

Nothing has been run.

What we do

Why one run gives every pass

In the model's code (modeling_inkling2_loop.py in transformers), each pass of the loop starts again from the state before the loop. The only thing a pass gets from the one before is a message, read by learned gates at each of the 12 looped layers. Nothing tells a layer which pass it is on or how many are to come. So passes 1 to k of a 20-pass run are exactly the passes of a k-pass run, and one forward pass per question at loop_num_passes=20 holds all of them: 6 visits before the loop, 240 inside it, and 6 after, 252 in all.

The six layers after the loop, 18 to 23, see only the last pass. To learn what the model would answer after pass k, we run those six layers again on pass k's states at every position, for each k from 1 to 20. That is the computation a k-pass model does, and it is checked against real runs at 1, 2 and 3 passes before anything else (below).

The input and the two positions read

Each question goes to the model as the challenge puts it: its chat format, thinking off, ending at the challenge's read position. At that position the model's next token is not the answer but a format marker: in the all-visits experiment the last visit read <|content_text|> and <|content_thinking|> as its top two on every practice question. So we add one token, the marker the model writes there at the normal 3 passes, and read two positions in the same forward pass. Because the model is causal, the added token changes nothing at the positions before it.

The answer position, after the added markerThe model's own output, as it would be with k passes: its top 10 tokens, the top one being the token it would answer with, and the rank of its 3-pass answer when that is not in the top 10

The logit lens is the one of the all-visits experiment: the model's own final norm and unembedding applied to the state entering each visit, with no trained weights. The visits before the loop are the same at every pass and are read once.

The added marker is the 3-pass one at every k. If after some pass the model would write a different marker, the read-position output shows it, and the answer position then shows what it answers given the usual one.

The two counts

One count for each part of the claim, both on the same footing at every pass:

  • Intermediate found, I(k): the number of questions whose intermediate is in the logit lens's top 10 at one or more of the 18 visits of pass k (its 12 looped visits and the six final layers run after it). The match is exact, in any case, with or without a leading space, as in the all-visits experiment. Every pass gets the same 18 visits, so a later pass has no more chances than an earlier one.
  • Answer kept, A(k): the number of questions on which the model's answer after pass k is its answer after pass 3.

The counts say where to look; the grid is what is read. Decided beforehand, for each question: the first pass at which the intermediate is in the top 10, and whether it stays; whether the answer changes, and to what; whether the rows of one pass look like those of the pass before. Every question is in the grid, none picked out.

How the results are shown

The readout grid of the all-visits experiment, one question at a time, with one change for 20 passes. Under the prompt and options, one line of 20 entries, one per pass, each giving the answer after that pass, the intermediate's best rank in it, and the 3-pass answer's rank when it is not in the top 10. Pressing an entry opens that pass below: the 12 looped visits and the six final layers run on it, as rows of the usual table. "← Pass" and "Pass →" step through the passes and are kept apart from "← Previous" and "Next →", which change the question. The layers before the loop are shown once, with pass 1.

The practice questions and WorkspaceBench get their own result files, their own section under Results and their own grid. WorkspaceBench's three files (basic, multihop, multilingual) share one grid with a line of buttons, as in the all-visits experiment. The viewer is built once the first results are in, and the design rules get its rule then.

Where it runs

On our own GPU, an A100 with 80 GB, with the transformers model and local weights in bfloat16. Not on NDIF, whose hosted model has its pass count fixed, and nothing runs on the Mac. A question is one forward pass of 252 visits and 20 short reruns of the last six layers; the 248 questions are a short job.

Competing explanations

  • More passes refine. Recurrent-depth models get better with more passes at test time (Geiping et al., 2025), but they were trained with the number of passes varied at random. Inkling 2 Mini was not, so this side has the weakest support here. It predicts I(k) rising past pass 3 while A(k) stays high.
  • The loop settles. All passes after the first share their weights and are linked only by the message, so the passes may settle where one more pass changes little. No paper in our readings tests this on this model. It predicts both counts flat from about pass 4, and rows that look alike from one pass to the next.
  • The loop breaks past 3. The model was trained only at 3 passes (model card, nnsight post), and Lee et al.'s coordinate turns negative after pass 3, as if the model expects no more. A fourth pass gets a message it never saw in training. It predicts A(k) falling, I(k) falling with it, and readouts drifting to tokens unrelated to the question.
  • The loop cycles. The same coordinate differs between passes 2 and 3 although the code runs them identically, so the message itself must carry where the model is in its passes. If it carries it as a cycle, later passes repeat an earlier pattern. It predicts counts going up and down with a regular period.

The four predict results different in kind: up, flat, down, or alternating.

Other reasons a result could arise:

  • Rounding. Twenty passes in bfloat16 could drift through rounding alone and look like a break. The practice questions are run again in float32; if their readouts at pass 20 agree with bfloat16, rounding is not the cause.
  • A rise from more chances to match. Ruled out by the count: each pass is read at the same 18 visits, and I(k) is never accumulated over passes.
  • A rise from drift that happens to hit the intermediate. If the readouts wander, a near-neighbour of the question (the next day, a nearby number) can turn up by chance. A(k) shows whether the model is still answering when it does. On WorkspaceBench's two-hop questions, where the intermediate is not the answer, nothing rules this out, and the grid has to be read.
  • The added marker. It is the 3-pass marker at every pass. If later passes would write another marker, the answer position reads the model in a state it would not have reached by itself. The read-position output says when this happens, and such questions are counted apart.
  • Matching. Exact matching misses some forms of an intermediate, the same at every pass, so it cannot make a rise or a fall.

What we expect

The thresholds, on WorkspaceBench's 238 questions; on the 10 practice questions the counts are too small to decide anything, and those are read by eye. Written on 25 Nov 2026 by the agent that drafted this page; the project's owner has not reviewed them.

  • Refine. At some pass from 4 to 20, I(k) is at least I(3) + 12, five per cent of the questions, while A(k) is at least 214, nine in ten.
  • Settle. At every pass from 5 to 20, I(k) is within 5 of I(3) and A(k) is at least 226, 95 per cent.
  • Break. By pass 10, A(k) is 119 or less, half the questions.
  • Cycle. From pass 4 on, I(k) or A(k) moves by 12 or more between neighbouring passes, with the same period at least three times in a row.
  • Anything else is reported as undecided and read in the grid before anything is built on it.

The agent's own guess is a break, slow at first: a fourth pass gets a message the model never saw in training, and nothing in it is trained to stay stable. A result that settles would not surprise it.

What would make us distrust a result

  • Passes 1 to 3 of the 20-pass run, with the final layers run on pass 3, do not give the same top 10 at all 48 visits as a normal 3-pass run of the same question. Then the passes are read wrongly, or the rerun of the final layers is not what the model does. Checked first, before anything is saved.
  • The model's output after pass 1 or pass 2 differs from a real run with loop_num_passes set to 1 or 2. Then the rerun of the final layers is wrong.
  • Adding the marker changes any readout at the read position. Then the model is not reading causally as we assume.
  • The practice questions in float32 disagree with bfloat16 at pass 20 on most questions. Then late passes reflect rounding, and only the passes before the disagreement are read.

Two limits that hold whatever the result. The local model already disagreed with NDIF's readouts at about one visit in ten, through rounding; every comparison here is between passes of the same local run, so this does not touch them, but the pass-3 readouts here will not match NDIF's exactly. And the challenge scores the model at 3 passes, so nothing here goes into a submission directly: it says what the loop does with more passes, and which pass the intermediate comes from.

All questions are run at once, with no single-question pilot first: the owner judged the run simple enough on 25 Nov 2026. The checks above still run first, inside the same job, and nothing is saved if they fail.
